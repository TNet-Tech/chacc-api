    Core API¶

    ChaCC API includes a small set of built-in endpoints for service discovery, health checks, and module lifecycle management. Additional endpoints are mounted by modules.

    Root¶

    GET /

    Returns a welcome message and points users to the FastAPI documentation.

    {
  "message": "Welcome to the ChaCC API Backbone! Check /docs for API modules."
}

    Health checks¶

    Basic health¶

    GET /api/health

    {
  "status": "healthy",
  "mode": "development",
  "checks": {
    "api": "ok"
  }
}

    Readiness¶

    GET /api/health/ready

    Runs a lightweight database query and reports whether the API and database are ready. Returns 200 when everything is ready and 503 Service Unavailable (with "status": "unhealthy") when the database cannot be reached, so load balancers and Kubernetes readiness probes stop sending traffic to the instance.

    {
  "status": "healthy",
  "mode": "development",
  "checks": {
    "api": "ok",
    "database": "ok"
  }
}

    Liveness¶

    GET /api/health/live

    {
  "status": "alive",
  "mode": "development",
  "checks": {
    "process": "running"
  }
}

    Module management¶

    Module management endpoints are available under the Core tag. When an authentication module is loaded and registers get_current_user, these routes require a bearer token. Without an authentication module, the core routes are open.

    Install a module¶

    POST /api/modules/

    Upload a .chacc archive as multipart form data.

    curl -F "file=@billing.chacc" http://localhost:8085/api/modules/

    Response:

    {
  "message": "Module 'billing' installed/updated successfully. Restart the server to apply changes (POST /api/system/restart).",
  "warnings": []
}

    Validation:

    • File name must end with .chacc.
    • Archive must contain module_meta.json.
    • module_meta.json must contain name.
    • The module's Python packages are installed into the packages folder before the archive is saved. If that fails nothing changes: 409 conflicting requirements, 422 requirements that can't be resolved, 503 package index unreachable.
    • A server restart is required to activate the new module.

    List modules¶

    GET /api/modules/

    {
  "modules": [
    {
      "name": "authentication",
      "display_name": "Authentication Module",
      "version": "0.1.0",
      "author": "ChaCC",
      "description": "Authentication support.",
      "is_enabled": true,
      "base_path_prefix": "/auth"
    }
  ]
}

    Enable a module¶

    POST /api/modules/{module_name}/enable

    Marks a module enabled in the database, installs its Python packages (same errors as upload), and requires a restart to mount it.

    Disable a module¶

    POST /api/modules/{module_name}/disable

    Marks a module disabled in the database, removes its extracted code directory, and requires a restart to unmount it.

    Uninstall a module¶

    DELETE /api/modules/{module_name}/uninstall

    Removes:

    • The module archive from .modules_installed/.
    • The extracted module directory from .modules_loaded/.
    • The ModuleRecord from the database.

    A restart is required to complete the uninstall.

    Module details¶

    GET /api/modules/{name}

    Everything about one module: what module_meta.json declares (license, links, required ChaCC version), its state, its routes, the modules it requires and the modules that use it, its Python packages with the installed versions, its archive (file, size, SHA-256) and its README. Returns 404 for an unknown module.

    state.code is one of:

    Code Meaning
    loaded Running now.
    pending Enabled, loads after a restart.
    stopping Disabled, still running until a restart.
    disabled Disabled.
    blocked Can't load: a required module or Python package is missing (state.reason).
    failed Failed to load (state.reason). In production the module is turned off.

    A failure is kept across restarts until the module loads, is enabled again, updated or uninstalled. The module list also reports it as load_failure.

    Dependency graph¶

    GET /api/modules/graph

    Returns the modules the server would load (installed archives in production, plugins/ in dev mode), the dependencies between them, which modules are blocked, disabled or not installed, and the load order.

    Module console¶

    Open /console in a browser to install, enable, disable and uninstall modules, view the dependency graph, check the services and restart the server. When the authentication module is loaded, the console asks you to log in.

    Click a module's name, or choose Details in its menu, to see everything about it, including why it failed to load. The link /console#module=<name> opens a module's details directly.

    The Services tab shows the database, Redis, rate limiting and the server, and checks them again every 30 seconds while the console is open. When a service is down or degraded, the tab and the status in the top bar say so.

    Server discovery¶

    GET /.well-known/chacc is never prefixed. It returns the server's api_prefix, a boot_id that changes on every restart, and auth (whether core routes need a login, and the login path).

    Restart the server¶

    POST /api/system/restart

    Applies module changes. Returns 202, or 409 if the server was not started with chacc run server. Like the module routes, it requires a login when the authentication module is loaded. See Automatic Restarts.

    Service status¶

    GET /api/system/services

    Checks the services the server uses, all at once, each within 2 seconds:

    Service Shows
    database Engine and version, location.
    redis Address, version, memory used. disabled unless REDIS_ENABLED=true.
    rate_limit Storage and how many routes are limited.
    server Mode, version, Python, API prefix, start time, whether a login is required and whether restarting from the console works.

    Each has a status: ok, degraded (working with a fallback, for example rate limits counted in memory because Redis is down), down, or disabled (not set up). The top-level status is the worst of them, with disabled counting as ok. message says what is wrong, hint what to do, description what the service is for, and error holds the original error. Passwords are never returned.

    {
  "status": "down",
  "checked_at": 1763380000.0,
  "services": [
    {
      "id": "redis",
      "name": "Redis",
      "status": "down",
      "description": "Optional. A fast shared store: ...",
      "message": "Nothing is answering at redis:6379.",
      "hint": "ChaCC keeps running and reconnects when Redis is back.",
      "error": "Error 111 connecting to redis:6379. Connection refused.",
      "details": [{"label": "Server", "value": "redis:6379"}],
      "latency_ms": null
    }
  ]
}

    It is open in development mode. In production it requires a login when the authentication module is loaded. For load balancers and Kubernetes, keep using /api/health/ready, which only depends on the database.

    Rate limiting¶

    Routes are limited only when they use rate_limit or shared_rate_limit from chacc_api.rate_limit (see Rate limiting). Over the limit, the client gets 429 with a Retry-After header:

    {"detail": "Too many requests. You have exceeded the rate limit of 10 per 1 minute."}

    A route's error_message replaces the detail text.

    Clients are counted by IP. Counts are kept in memory unless RATE_LIMIT_STORAGE_URI points to Redis. See Configuration.
